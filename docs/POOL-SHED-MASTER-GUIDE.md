# The Pool Shed — Master Guide

**Owner:** Pool Bros Limited · **System:** The Pool Shed · **Baseline audited:** v1.47.6 (local copy, 19 November 2026)
**Supersedes:** the ChatGPT handover "Complete System Handover, Business Requirements and Development Specification".

This guide is for anyone (human or AI) developing Pool Shed. It replaces assumptions with what the code actually does, ranks the real problems by business risk, and sets out a step-by-step plan to fix them **without wiping or losing a single live record**.

## 1. The five rules that override everything else

1. **Live data comes first.** No change ships unless the data that exists today survives it, provably. A backup that has not been restored in a drill does not count as a backup.
2. **Additive, reversible, verified.** New structures are added alongside old ones, filled from them, checked against them, and only then switched over. The old store stays readable as an archive. Every step has a written rollback.
3. **Production is never the test bench.** Changes are proven on a copy (staging project or Supabase branch) loaded with a recent copy of real data.
4. **Behaviour, not text.** A feature is done when a test proves the behaviour (data saved, permission enforced, totals reconcile), not when a string exists in a file or a build passes.
5. **Say exactly what is true.** "Deployed" is not "verified". "Code exists" is not "working". Integrations (Xero, email, Azzy) are only called live when shown working with real authorised records.

### The continuity promise (owner's requirement, 20 Nov 2026)

This is an upgrade of the existing system, **not a new system**. Every record staff have entered (customers, products, suppliers, sales and purchase orders, payments, stock and goods-in history, jobs, quotes, audits, notes) stays in the app and appears in its usual place after every phase. Concretely:
- No phase starts from an empty database or asks staff to re-enter anything.
- Every phase ends with `node scripts/phase0/continuity-check.mjs <previous snapshot> <current snapshot>`. It must print `PASS · every earlier record is still present`. New records and normal staff edits are allowed and listed; a missing record blocks the release until it is explained.
- When data moves to new tables (Phase 3), the old snapshot stays as a read-only archive, and the screens are checked to show the same records with the same totals before the switch.
- Only duplicate **safety copies** (old workspace revisions) are ever pruned, and only after a verified backup that contains them.

## 3. Audit findings, ranked by business risk

### F1. Supabase egress: a 5-second poll downloads the whole business [Verified] — Critical

`01-legacy-01.js:1301` and `:1358`. Every signed-in tab runs `refreshSharedWorkspaceFromRemote` **every 5 seconds**. It requests `select("data,updated_at")`, the **entire** workspace, and only *then* checks whether `updated_at` has changed. It does not pause when the tab is hidden or the iPad is asleep in a browser tab.

At the same time, a realtime subscription (`:1341`) on the same row pushes the full record to every open tab on every save. `database/013:125` would set `replica identity full`, but migration 013 is **not applied on live** (see F10).

**[Verified 19 Nov 2026, live data]** One full check returns 7.07 MB of JSON (0.49 MB gzip-compressed). One open tab makes 720 checks an hour, which is 0.34 GB/hour compressed or ~5 GB uncompressed. The whole 11.51 GB overage equals about **34 tab-hours**, roughly one tab open for four working days. Live also has **no tables** in the `supabase_realtime` publication, so the realtime channel never delivered anything; the poll did all the damage.

**Fix (low risk, no data change):** poll only `updated_at` (a few bytes) and fetch `data` only when it changes. Stop polling while the tab is hidden. Lengthen the interval to 30–60 s when realtime is connected. Use realtime as a "something changed" signal rather than the data carrier. Expected egress cut: **95–99 %**.

### F2. The revision table stores a full copy of the business on every save [Verified] — Critical

`database/013:107`. Each `ps_workspace_save` call inserts the entire previous snapshot into `ps_workspace_revisions`, and nothing ever deletes old rows. Saves fire 650 ms after any edit (`01-legacy-01.js:1363`). **[Verified]** Live on 19 Nov 2026: 314 copies since 27 Sep take **210 MB of the 229 MB database** (500 MB free-tier cap). Restores and backups also get slower each day.

**Fix:** keep it as the safety net, but add retention: keep everything from the last 7 days, then one per day for 90 days, then one per month. **Only after** a verified external backup. Later, normalised tables (Phase 3) replace whole-document revisions with per-record history.

### F3. Every user can read everything, whatever their role [Verified] — Critical (security and commercial)

`database/002:23–34`. The read policy on `workspace_snapshots` checks only workspace membership. Any member (engineer included) downloads the full JSON, including supplier costs, margins, customer finances and supplier payments, and can see it in the browser's network tab. Role permissions only hide screens. This breaks the guide's own rule 16.

**Fix path (revised 20 Nov 2026):** done in Phase 3 with per-table row-level security. Stripping fields from the single shared document (the original Phase 2 idea) is unsafe: an engineer's save would write the stripped copy back. Live has only Admin users today, so nobody is exposed; **do not issue Engineer accounts to people who must not see costs until Phase 3.**

### F4. One document means multi-user saves collide [Verified] — High

All staff write the same row. Optimistic locking (`expected updated_at`) with client-side merge prevents silent overwrites (good), but:
- every save uploads the whole business;
- any two near-simultaneous edits anywhere conflict and need a merge;
- the merge runs in each browser, with up to two retries.

This is the root of the historic "lost changes / refresh data loss" reports. The durable fix is per-record tables (Phase 3).

### F5. Save validation gets slower as history grows [Verified] — High

`database/013`, ledger loop. For `receiptEvents` and `putawayTransfers`, every old entry is compared against every new entry (n × m `jsonb` equality) **on every save**, while holding a lock. Saves will slow down, then time out, as goods-in history grows.

**Fix:** compare by `id` set with a hash, or (Phase 3) make ledgers append-only tables protected by a trigger.

### F6. Start-up weight [Verified] — High (staff time, iPads)

- `index.html` pulls **~5.1 MB** of uncompressed local JS, CSS and images across 67 scripts before the app is fully usable. The main script is 1.16 MB (≈240 KB gzipped), and the CSS is 966 KB (≈140 KB gzipped).
- Every asset is served `Cache-Control: max-age=0, must-revalidate` (`vercel.json`), although all URLs carry `?v=1.47.6`. Every page load therefore makes ~70 revalidation round-trips. Versioned assets should be `immutable, max-age=31536000`.
- The logo `pb-logo.png` is **420 KB**, used at 38 px and as the favicon. A 64 px WebP is ~6 KB.
- After start-up, the service worker warms the Pool Audits Babel (2.3 MB), React and Tailwind compiler for every user. **Kept in v1.48:** offline iPad audits depend on it, and it costs Vercel bandwidth, not Supabase. Revisit when Pool Audits is pre-compiled (Phase 4).
- Pool Audits compiles its JSX in the browser on every open: slow on iPads.

### F7. Server functions also download the whole business per call [Verified] — Medium

`api/quote.js`, `project-review.js`, `project-email.js`, `workspace-health.js` and the Azzy context (`server/azzy-pool-shed.js`) each fetch the full snapshot to read one job, extra or quote. This causes Vercel time and Supabase egress per click, and the 60 s timeouts seen with Azzy.

### F10. Live database is behind the code [Verified] — High

The live `ps_workspace_save` is the pre-013 version. It has no "refuse to erase all customers/products" safety lock and no inactive-user block, and the `ps_workspace_revisions` index is missing. The realtime publication is empty. Phase 2 replaces 013 with `014`, which keeps the safety rules but leaves realtime off (v1.48 egress fix). Tested on staging 20 Nov 2026.

### F9. What is already good [Verified]

- The customer portal is isolated and served with a strict CSP, no-referrer and no-store.
- Saves use optimistic locking with conflict merge, plus server-side safety locks against emptying core arrays or making stock negative.
- Quote acceptance has an atomic RPC (`ps_quote_accept_atomic`) and a conversion job queue (`database/009`), the right foundation for "no duplicate orders".
- The revisions table, though unbounded, means recent history is recoverable today.
- `@electric-sql/pglite` and `playwright-core` are already dev dependencies, so real database and browser tests need no new tooling.

## 5. Data protection protocol (Phase 0, mandatory before any change)

Run in this order and record the results in `docs/RELEASE-LOG.md`.

1. **Freeze point.** Announce a 15-minute no-edit window.
2. **Database backup.** `pg_dump` of schema and data from the live project (Supabase dashboard → Database → Backups, plus a `pg_dump` you hold yourself). Store two copies off-platform.
3. **Snapshot export.** Save the `workspace_snapshots` row for `pool-bros-main` as JSON, plus the latest 50 rows of `ps_workspace_revisions`.
4. **Storage backup.** Download every object in every bucket (`supabase storage` CLI or a script using the service key on your machine; never in the browser). Record the file count and total bytes per bucket.
5. **Fingerprint.** Record counts and checksums: number of customers, products, suppliers, sales orders, purchase orders, jobs and stock lines, plus the sum of SO totals, PO totals and stock value. These become the "nothing lost" baseline for every later phase.
6. **Environment inventory.** List the names (not values) of every Vercel env var and Supabase secret.
7. **Source.** Put this folder under git, compare it with GitHub `main` and the v1.47.7 branch, and tag the live baseline `v1.47.6-live`.
8. **Restore drill.** Restore the backup into a separate Supabase project (staging) and confirm the fingerprint matches exactly. **No phase starts until this passes.**
9. **Staging.** Point a Vercel preview deployment at the staging project. All work is proven there first.

Rollback for every later phase: redeploy the previous Vercel build (one click) and, if data was touched, restore from step 2/3 and replay changes made since (the revisions table holds them).

## 6. Roadmap

Each phase lists: goal · changes · data risk · proof · rollback. Phases 1 and 2 can ship within days of Phase 0. Phase 3 is the big one and runs module by module.

### Phase 1 — Stop the bleeding (no schema or data change)
- **Changes:** fix F1 (lightweight poll, pause when hidden, realtime as a signal only); `replica identity default`; immutable caching for versioned assets; 6 KB logo/favicon; service worker stops pre-caching the audit vendor bundle; fix the `vercel.json` duplicate; remove design-lab routes.
- **Data risk:** none. Reads and caching only.
- **Proof:** measure bytes per session before and after on staging (target: under 2 MB per hour per idle tab); concurrent-edit test still passes.
- **Rollback:** previous Vercel deployment.

### Phase 2 — Protect money data and the database
- **Changes:** revisions retention job (after the Phase 0 drill); ledger validation by id-hash (F5); role-filtered read RPC so engineers receive a snapshot with costs, margins and finance stripped server-side; the direct `select` policy limited to admin/operator roles.
- **Data risk:** low. Retention deletes only old duplicate copies, already exported in Phase 0.
- **Proof:** an engineer account cannot obtain cost or margin data by any route (UI, network tab, Azzy); save time stays flat with 10× synthetic ledger history.
- **Rollback:** restore the policy and function definitions from the migration file.

### Phase 3 — Move from one document to proper tables, without losing anything
The pattern for each module (customers → products → suppliers → stock ledger → sales orders → purchase orders → projects):
1. **Add** the new tables (stable IDs = the existing JSON `id`s, `workspace_id`, `version`, `created/updated_at/by`, soft delete) with row-level security by role.
2. **Backfill** from the live snapshot in one transaction. Check row counts and value checksums against the Phase 0 fingerprint.
3. **Dual-write:** the app writes both the snapshot and the table; a nightly job compares them and reports any difference.
4. **Switch reads** to the table for that module only (paginated, searched server-side).
5. After 2 clean weeks, **stop writing** that section to the snapshot. The snapshot stays as a read-only archive. Nothing is deleted.
- **Proof per module:** continuity check PASS (every existing record present), fingerprint match, concurrency test (two users edit different records and both survive), permission test, reload test.
- **Rollback per module:** flip reads back to the snapshot, which dual-write kept current.

### Phase 4 — The new interface ("Deep End" design)
- Approved direction: calm white and grey with pool blue, logo yellow for actions and red only for problems; light and dark modes, with every text pair checked at 4.5:1 or better; grouped navigation; clickable dashboard (Needs you, Work in progress, Performance, At a glance); status lists with search, owner filters, bulk actions and a **Ready to invoice** queue for accounts.
- Design reference: Claude canvas "Pool Shed Redesign", artboards B · Deep End (light and dark).
- **Changes:** one token stylesheet (light and dark) replaces the 42 CSS layers; screens are rebuilt one module at a time behind the same data functions; Pool Audits is pre-compiled (no in-browser Babel).
- **Data risk:** none. The UI only reads and writes through the existing save functions.
- **Proof:** Playwright run of every main workflow in light and dark, desktop and iPad; accessibility contrast check.

### Phase 5 — Quote Studio replaces Quotient
Keep all the ChatGPT requirements (section 9 of the old guide): versioning, options, e-signature, follow-up and expiry, offers with a **20 % net-margin floor**, follow-up queue and reporting. Build on the existing `ps_quote_*` tables and atomic acceptance. Reminders run from a **Vercel Cron** job with idempotency keys (never from an open browser). Cut over only after scenario U passes with three real quotes.

### Phase 6 — Finance, Xero, labour and hire
Verify Xero OAuth, webhooks and retry queue against real authorised records. Three-way matching. Labour in days/half-days excluding weekends. Hire accrual with daily confirmation. The project statement must never double-count PO → bill → payment.

### Phase 7 — Azzy
Only after Phase 2: Azzy reads through the same role-filtered functions as the user, links every fact to its record, and only proposes actions (a human approves).

## 7. Business rules (never break)

1. Customers never see costs, margins, stock, POs, staff notes or other customers.
2. Accepted prices, options and terms are frozen; catalogue changes never alter them.
3. Missing supplier costs are flagged, never invented.
4. Main Warehouse is the default stock source; other locations only by deliberate choice.
5. Stock moves are atomic and audited; no negative stock without an approved, logged exception.
6. One acceptance creates exactly one Sales Order (and Project where relevant), even on retry.
7. Extras stay separate from the original scope, are counted once, and only when approved.
8. PO, supplier bill and payment are stages of one cost, never three costs.
9. Labour is charged in days/half-days, excluding Saturdays and Sundays unless approved weekend work.
10. Ongoing labour and hire require periodic confirmation.
11. Minimum gross margin 20 % of net revenue (configurable; breaches need an audited approval).
12. Corrections create history; nothing financial is silently deleted.
13. Permissions are enforced on the server, not just hidden in the UI.
14. Integrations are not called live until proven with real records.
15. No demo data, demo logins or developer controls in production.

## 8. Module requirements (condensed)

The detailed field lists in the ChatGPT guide sections 6–25 remain the requirements reference. Additions from this audit:

- **CRM:** duplicate check by email, phone and postcode before create; acceptance updates the existing customer.
- **Product Hub:** server-side search (name, partial, SKU, supplier SKU, typo-tolerant via `pg_trgm`); imports staged in a table with preview and undo, never through browser storage.
- **Stock:** quantities as a ledger (movements) with balances derived, not edited.
- **Sales Orders:** statuses New → Part stock → Ready to pick → Packed → Dispatched → **Ready to invoice** → Invoiced, each with a target time and "waiting too long" flag.
- **Purchasing:** Draft → Awaiting payment (proforma) → Sent → Part received → To bill → Closed; goods-in blocked before Sent.
- **Dashboard:** every number opens the filtered list behind it.
